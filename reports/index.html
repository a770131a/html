C. 後續 Issue 格式與狀態定義

為了讓網站可以統一狀況，後續每一張 Issue / MD 都應該有固定欄位，讓報告頁可由 manifest 或 GitHub Actions 自動產生，而不是手工改 HTML。
欄位用途範例
type區分目前工作與 Roadmapcurrent / roadmap / pmqa / model_training
status工程狀態planned / design_ready / in_progress / implemented / review_pending / accepted / blocked
pmqa_status驗收狀態not_started / local_pass / api_uat_pass / accepted_with_known_gaps / accepted / blocked
area責任範圍Backend / Frontend / Agent / XDR / ITAM / Compliance / RBAC / AI Training
priority優先級P0 / P1 / P2
mvp_percent報告頁顯示進度0 / 25 / 50 / 75 / 100
available_evidence已有證據unit_test, api_uat, build_pass, redacted_artifact
missing_evidence缺口deployed_screenshot, real_device_soak, audit_log, golden_replay_report
blocker_level阻塞層級none / beta / ga / hardening
public_summary_safe是否可公開摘要true / false

C1. 標準 Status 字典

planned

已列入 Roadmap，尚未開始。

design_ready

規格足夠，可交工程開發。

implemented

工程完成或 PR merged，但不等於驗收通過。

review_pending

等待 PMQA、UAT、截圖、replay 或安全證據。

accepted_with_known_gaps

可條件通過 MVP，但有 GA/部署/真機缺口。

accepted

PMQA 證據完整，可正式標記完成。

blocked_beta

阻擋 Beta readiness。

blocked_ga

不阻擋 MVP，但阻擋 GA/hardening。

C2. 網站統一狀況的資料流

Step 1
Issue / MD 固定格式

每張 issue 都填 type、status、pmqa_status、priority、evidence、missing_evidence、mvp_percent。

Step 2
產生 progress_manifest.json

由腳本掃 docs/dev_master_status_index.md、issues、PR metadata，合併成單一狀態資料。

Step 3
GitHub Actions 自動產生 HTML

每次 push 或 issue 更新後，重新產生 reports/index.html。

Step 4
Public Summary Mirror

只把安全摘要同步到 public repo；主程式與完整 MD 保持 private。
